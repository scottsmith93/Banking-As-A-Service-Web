# Bank movements

### 2026-10-23 — Shared source and amount refinements

Source cells pair bank provenance with illustrative photo avatars, card names and cardholder names where applicable. In Bank movements, the person/shop asset is a compact badge over the bank mark. The overview alone hides the bank mark; both the overview and All show completed justification only, while To justify retains its action states. Signed inflows use bold green figures and regular-weight plus signs. Shared status pills have no border, a 5% semantic tint and matching text. Demo headshots are external illustrative images, not actual portraits of fictional account owners; Carbon's person icon is the offline fallback.

## Purpose

Provide one cross-bank workspace for browsing transactions and justifying them with invoices or categories. The account overview is a ten-record window into this same activity, not a separate full transaction workspace.

## Audience

Stakeholder review and engineering handoff.

## How to find it

`/banking/bank-movements` from the left navigation. `?account=sage-operating-account&view=all` selects an originating account; `transaction` opens a transaction panel. `view=needsAction` and `view=matched` select To justify and Justified. Legacy per-account transaction URLs redirect here.

## Key decisions

- All uses the overview's shared column set, amount/type/evidence renderers and white-row/horizontal-rule styling, with no Payment status column and blank unfinished Justified cells. Cross-bank Source is the intentional exception: a constant-width bank mark with a smaller overlaid person/shop badge keeps every text start aligned. To justify retains its existing proposal/actions workflow.
- The account selector shows bank icons, account names and masked references, with Carbon's bank icon for All bank accounts. Choice labels and assistive names include both bank and account identity. Bank selection still commits only on click/Enter, preserves URL context and hides Sage-only owner filtering for other banks.
- Transaction-type selection tags explicitly opt into the shared rounded, borderless 5% tint; Carbon retains checkbox selection, tag removal, focus and keyboard handling.

- Account overview View all transactions, row selection, account navigation and bank-list task actions all open this workspace with account context. Account and tab selection survive refresh and browser Back through URL parameters. Direct entry initially shows all accounts and All transactions.
- Account selector and three KPIs occupy the left side of an unboxed desktop control band, with search and filters aligned to the right on the same row. Labels use Sage's 14px token and values 16px, both left-aligned; the KPI cluster retains intrinsic content widths and 24px gaps. At a workspace container width below 1200px the sections wrap with 16px separation rather than compressing unreadably. Compact Carbon inputs and single-line selected-pill text keep the default desktop band short; full option labels and Carbon checkbox multi-selection remain available in the dropdowns. Date/amount ranges remain in the Filters panel.
- Search, cardholder and transaction-type fields are capped at 320px and wrap as needed. Cardholder is a Carbon multi-select with visible Carbon checkboxes, shown only for a specifically selected Sage account, not a regular bank or the all-bank scope. Transaction type is a multi-select for every bank. The option owns row clicks, keyboard behaviour and `aria-selected`; its checkbox mirrors checked state without a duplicate tab stop or nested screen-reader control. Selected choices are OR-ed within each group and AND-ed between groups. All is an actual selected Carbon option with black text, not a grey placeholder. The compact default summary says All; expanded options and accessible labels retain All cardholders / All transaction types. Specific selected names may wrap instead of overflowing. Switching banks clears filter selections, and hidden cardholder selections never restrict regular-bank rows. Carbon's compact pagination layout is enabled at tablet widths so translated navigation labels remain contained.
- The shared category cell centres its small green tick against the category name in both recent and full transaction tables, without repeating a Categorised label.
- Bank and ledger balances are independently supplied mock snapshots. Amount to justify is computed in cents from actionable transactions for the selected account(s); it is not a bank-minus-ledger difference. Search and secondary filters do not change these account-level KPIs.
- Tabs are All, To justify, Justified. All/Justified deliberately use lighter browsing/outcome columns; To justify exposes proposals and contextual actions as a work queue. This is the same grid and shared data, not a technical restriction on All. Processing status remains separate: All includes payments that are not yet eligible for justification as well as failed/cancelled items.
- Bank transaction amounts retain locale-aware +/− signs (zero stays unsigned). All negative transaction values now use the shared dark-red money-out token and bold figure with a regular-weight minus, including To justify, the overview and detail/review panels. All/Justified retain green positive transaction values. Bank amounts and suggested invoice totals are vertically centred in their complete cell while staying right-aligned. Proposed invoice totals are separate from signed cash flow and are never direction-coloured. Completed category cells show only a tick and the category, without a repeated Categorised label.
- `useTransactionTableColumns` is the single definition of column order, headings, formatting and cell content. The ten-row overview renders it through Carbon FlatTable; the full workspace renders it through the shared SageDataGrid adapter with sorting, keyboard access and Carbon pagination. There are no independent copies of the table cell design.
- Both views consume the same transaction context. Invoice association and category changes immediately update justification displays, KPIs and task counts across routes. Invoice links open Purchases and offer a return to the originating movement.
- Existing sequential suggested-invoice review is retained alongside the inline To justify actions. Both use the same candidates and eligibility checks; ambiguous cases require an explicit invoice choice.

### To justify workbench

- Bank movements now uses the full content width with 40px left/right gutters, including the table. All queues use 20 transactions per Carbon pagination page; the account overview remains a ten-record recent window.
- Source replaces the dedicated Cardholder column in all tabs and the shared ten-row overview. It shows the bank logo (except in the single-account overview) and a Carbon photo Portrait with card name and cardholder only when a Sage Wallet transaction has a cardholder and card reference. Non-card and regular-bank activity never invents a cardholder. Hover and keyboard focus retain full translated provenance, and the Sage-only multi-select cardholder filter is retained. External illustrative demo photos fall back to Carbon's person icon when unavailable.
- To justify groups Source, Date, Description and Amount under Bank transaction, with Suggestion and Action under Suggested justification. These headings apply to invoice, category, transfer and cash-withdrawal tasks rather than assuming every transaction is a purchase invoice. A restrained inset divider distinguishes bank facts from proposed evidence. Descriptions pair plain text with the transaction-type icon/label, without repeating owner/account names already represented by Source.
- Task rows use a 72px minimum instead of 88px, retain 4px top/bottom cell padding and a 2px gap between description/type, and expand for translated or longer proposal content. Justify and Review share a row where they fit, wrapping when necessary. Existing matching explanations, discrepancy checks and contextual actions are unchanged.
- A single eligible invoice exposes its reference, supplier/date, numeric EUR total and actual matching reasons, with Justify and Review actions. Multiple eligible invoices require an explicit review/choice; no candidate is silently selected. No confidence percentage is invented.
- Invoice issue date and bank transaction date are deliberately distinct. Suggestions may use an earlier invoice within the existing 31-day mock window, not necessarily the same date. Shared proposal summaries explicitly label the invoice date and state when it is the day before, multiple days before, or after the transaction. This timing copy is shared by table proposals, detail-panel candidates, existing-invoice search and sequential review. Later-dated invoices remain ineligible; an earlier date alone is not an amount mismatch. The 31-day window is a prototype rule, not a claim about universal accounting policy.
- Related supplier invoices with an amount difference are review-only. Missing evidence opens the existing equal-weight link/upload controls. Category-only transactions open categorisation, never invoice upload. The existing eligibility and invoice-reuse guards remain authoritative.
- Inline confirmation updates shared state immediately, announces success and keeps a completed row visible for 1.2 seconds before removing it from To justify. The grid restores the next task cell only when the user has not moved to another control. Counts and outstanding amounts update from the actual records.
- With suggestions filters to eligible invoice proposals, including ambiguous candidates, not merely related documents with differences. Rejecting a proposal suppresses that candidate only and does not justify or remove the transaction.
- Proposal links open Purchases without triggering row selection. Unmatched invoices are labelled Proposed invoice rather than Transaction matched. Linked records continue to show the matched state.
- The extra British Telecom invoice is an intentional ambiguity fixture. Initial Sage totals remain 30 transactions, 16 actionable, 10 justified and EUR 3,397.75 to justify. The actionable breakdown is six single-invoice suggestions, one multiple-invoice case, six amount-difference cases, two missing-invoice cases and one category task.

## Localization scope

All touched labels and interaction states support English, Spanish, French, German and Portuguese. EUR and dates use the active locale. Account names and merchant names are fixture data.

## Known limitations

- There is no live backend or persistence. The shared session store is the API boundary; refreshing resets transaction changes. URL account/tab/transaction context persists independently.
- Balances in `bankMovementBalances.ts`, `bankingBaas.ts` and `bankAccountConnections.ts` are demonstration snapshots; they are not totals of the bounded transaction sample. Ledger snapshots happen to equal bank snapshots in this fixture, without claiming that invoice justification performs accounting reconciliation.
- The account selector includes the staged Sage demonstration accounts and existing connected-bank fixtures. Newly created page-local manual accounts are not a live banking feed.
- Upload extraction, matching eligibility and document preview limitations remain documented in `../banking-baas/transactions/README.md`.
- Connected-bank Source logos reuse the same compact external assets as the bank list, fully contained in circular masks without zoom/cropping. Unavailable images fall back to Carbon's bank icon while retaining the accessible bank/account name. A production bank API should supply approved compact brand assets rather than relying on external website assets.
